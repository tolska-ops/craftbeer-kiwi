# Concept Snapshot: AI Craft Beer Companion — Long-Term Vision

**One-liner:** A six-document vision set (Opportunity/Vision, Words of Wisdom, Risks and Mitigation, Private Beta Plan, AI Beer Concierge Strategy, Summary and Guiding Principles, User Journey) mapping craft.kiwi's evolution from brewery map to personal AI beer companion. Directionally sound and worth keeping as a north star — but written without visibility into this project's actual constraints and existing decisions, so it needs reconciling before any of it becomes active work.

## Why this exists

Andy brought back six planning documents from a Melbourne trip (loaded 2-3 August), covering product vision, founder advice, risk mitigation, a private beta plan, an AI concierge strategy, and a user journey. Worth capturing the north star and the specific contradictions in one place, rather than letting the vision quietly reshape scope before Phase 1 (Wellington directory) has actually proven itself — which is the project's own stated sequencing already.

**Likely origin:** the content reads as generated by an AI tool in a session with no visibility into this project's real state — no awareness of the actual `todo.md`, the current false-positive rate on automated discovery, or the auth decision already made. Worth noting for next time: feeding an AI tool the project's actual state before asking it to plan produces grounded advice instead of a solid-sounding but decontextualised playbook.

## The north star (worth keeping)

Directory → personal layer → AI companion is a sensible long-term arc:

1. **Stage 1 — the map.** Best NZ craft beer directory. Discovery only.
2. **Stage 2 — the passport.** User accounts, favourites, visit history. Turns anonymous visitors into a returning audience.
3. **Stage 3 — the companion.** Personalised recommendations, trip planning, natural-language search.
4. **Stage 4 — the concierge.** Full AI layer combining preferences, visit history, and craft beer knowledge (RAG-style: existing AI model + craft.kiwi's own data as the knowledge layer, not a custom-trained model).

This is already directionally consistent with existing project choices — `venue_type` is deliberately a string rather than a boolean specifically to leave room for a future pubs & bars layer, which is the same "build now for a future you can't fully see yet, without overcommitting" instinct.

**The genuinely good, non-generic advice worth keeping regardless of pace:**
- Fall in love with the problem, not the specific feature set — the product will change shape, the mission ("help people discover great NZ craft beer experiences") shouldn't.
- The Private Beta Plan's "what NOT to build yet" list — AI concierge, brewery accounts, reviews, social features, monetisation — already matches where the project actually is. This is the most grounded artefact in the set.
- "The account is not the product, the journey is the product" (User Journey) is a good design lens for whenever Stage 2 does get built.

## Where the vision set doesn't fit this project's reality

**1. Scale mismatch — written for a team, not 5-8 hrs/week.** The Private Beta Plan proposes recruiting and managing 50-100 targeted beta users with a structured feedback loop, then expanding to 500 invite-only users, run *alongside* Stage 3/4 AI development. That's an ongoing operational commitment on top of build work. As written, it would consume the entire weekly time budget and stall everything already sequenced in `todo.md`. None of the six documents name capacity as a risk at all — the Risks and Mitigation doc lists ten risks (directory-trap, Google Maps differentiation, data burden, monetisation timing, etc.) but misses the one most likely to actually bite for a solo founder: the roadmap's pace assumption doesn't match the builder's real capacity.

**2. Data-automation confidence doesn't match lived experience.** The Risks doc treats brewery data accuracy as solvable via "automated data collection, AI extraction, public information sources" — stated in passing, as a settled mitigation. In practice: `brewery-discover`'s first live run had a ~50% false-positive rate on bars vs. breweries (`DEC-015` era), the relocation/multi-site blind spot has been hit twice for real (Three Sisters, Te Aro Brewing — `TD-007`), and the two-source-agreement rule for closures exists specifically because single-source automation isn't trustworthy enough to act on alone (`DEC-005`). The AI Concierge doc's "Beer Data" requirements (flavour profile, hop intensity, seasonality, per-beer detail) are a materially larger and harder data-accuracy problem than brewery-level facts, which the project is *still* finding blind spots in. Not a reason to abandon the "avoid becoming a data-maintenance business" principle — just don't let the doc's confidence substitute for the project's actual, harder-won track record here.

**3. Direct contradiction — "architect region-independent from day one" vs. `TD-037`.** The Guiding Principles doc calls for building region-independent architecture now, to support future AU/US/UK expansion without a rebuild. This conflicts with `TD-037` (multi-country domain/branding strategy deliberately parked until Wellington is proven and national NZ rollout is actively underway) and with the automation-plan's own region-by-region rollout decision, made specifically because the first live run's error rate had no reason to be lower in an unfamiliar market with no personal gut-check to catch it. **Resolution: `TD-037`'s sequencing stands.** The vision doc's "future-proof from day one" line should be read as superseded, not as new guidance — it's exactly the "too much complexity too early" failure mode the project's own Risks doc warns against elsewhere.

**4. Direct contradiction — frictionless OAuth accounts vs. the deliberately-anonymous current design.** The User Journey doc's Stage 3 ("Continue with Google / Apple / email login link... minimal friction") describes a real auth system — OAuth providers, session management, a users table. The project's actual personal-data feature (trail/favourites, not yet built) is deliberately anonymous: `crypto.randomUUID()` in `localStorage`, chosen specifically to avoid building auth for a feature that doesn't need identity, logged in `security.md` as an accepted low-stakes risk ("no PII involved, avoids building a full auth system for a feature that doesn't need identity"). The vision doc treats real accounts as a small, natural next step; in practice it's the single biggest scope jump in the whole roadmap, and the one that also pulls in Privacy Act consideration beyond the breach-response process already documented. **Not resolved — flagged as a decision to make deliberately when Stage 2 is actually being scoped**, rather than one that should drift in via a vision doc's assumption.

## What this doesn't change right now

Nothing here is "buildable soon" in the sense `todo.md` uses that phrase. It's all Stage 2/3/4 material, correctly gated behind Phase 1 (Wellington directory, still single-region, 24 breweries) proving itself — which is already the project's stated sequencing, not a new constraint this doc is introducing.

## Related terms you'll bump into

- **RAG (Retrieval Augmented Generation)** — the AI Concierge doc's proposed architecture: an existing AI model plus a search step against craft.kiwi's own structured data, rather than a custom-trained model. Standard, sensible approach if/when Stage 4 is built — not a near-term decision.
- **North star metric** — the vision docs argue for measuring "successful craft beer experiences created" (visits planned, routes completed, return usage) over "breweries listed." Worth keeping in mind once there's usage data to measure against (Vercel Analytics, installed 27 July) — not actionable yet on its own.
- **Point-in-time snapshot vs. monitored** — the same distinction already named in `craftbeer-kiwi-concept-data-drift.md` applies directly to any future per-beer data (flavour, hop intensity, seasonality) the AI Concierge doc calls for — expect the same drift problem at a harder, more granular level.
